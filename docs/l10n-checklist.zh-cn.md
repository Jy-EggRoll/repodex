# 把这套 l10n 方案迁移到其他仓库

[English](./l10n-checklist.md) | 简体中文

本仓库的国际化分成两半：一半是只属于这份代码的具体实现，另一半是可复用的范式。本文是后半部分——一份把该方案复现到别处的清单。关于本地化在本仓库**如何运作**（文案包布局、运行时装配、如何新增文案），见 README 的[国际化](../README_zh-cn.md#国际化l10n)一节。

## 先把层次拆开

这套东西不是单一决策，而是四层，它们的可迁移性差别很大：

| 层次       | 是什么                                                                            | 可迁移性                             |
| ---------- | --------------------------------------------------------------------------------- | ------------------------------------ |
| 文件格式   | `l10n/bundle.l10n.json` 恒等映射 + `l10n/bundle.l10n.<locale>.json`，`{0}` 占位符 | 可以，但有前提（见下）               |
| 运行时装配 | i18next + 语言探测 + paint 前设置 `lang`                                          | 只有形态可搬，运行时随框架而定       |
| 强制约束   | 测试断言与排序脚本                                                                | 可以——最值钱、也最与技术栈无关的部分 |
| 线格式契约 | 兼作翻译键的错误码                                                                | 可以，但前提是错误码只有一个共享来源 |

文件格式不是本仓库的发明：英文原文作 key、`bundle.l10n.json` 是英文到英文的恒等映射，这是 VS Code 的 l10n 约定。格式本身和与之配套的抽取工具，写在 `@vscode/l10n-dev` 的 README 里：<https://github.com/microsoft/vscode-l10n>。

## 清单

1. **文案包布局。** `l10n/bundle.l10n.json` 存源语言的恒等映射，因此它同时兼任"所有已知 key 的登记表"。每种语言一个 `l10n/bundle.l10n.<locale>.json`。
2. **唯一的取词入口。** 只导出一个 `t(key, options)`，所有调用点（含组件）都走它。有两个入口就意味着有两处需要同步。
3. **断言：各语言的 key 集合完全一致。** 挡"翻译做了一半"的最廉价手段。
4. **断言：源语言包是恒等映射**（每条都满足 `value === key`）。这条挡住的是"去改源语言包而不是改译文包"这种改错地方的行为。
5. **断言：key 与各译文之间的 `{n}` 占位符一致。** 这条挡的是只在运行时才暴露的问题——译文漏掉或多出一个占位符。
6. **断言：运行期计算的 key 是闭合的。** 见下面[动态键](#动态键最容易漏掉的那条)。这是最容易被漏掉的一条，也是本仓库最近才补上的。
7. **排序脚本**，让 diff 只反映真实变更，而不是顺序噪音。
8. **在首次绘制前设置 `lang`**（HTML 入口里的内联脚本）。仅当首帧语言错误真的可见时才需要，否则可以不做。

第 3 到第 7 条是纯断言与约定，不依赖任何框架。第 2 条和第 8 条会随框架变形。

## 动态键：最容易漏掉的那条

"动态键"指运行期才算出、再传给 `t()` 的字符串，因此扫描字面量 `t("...")` 调用的做法看不见它。实践中会出现两类：

- **线格式取值。** 服务端返回 `error` 字段，客户端用 `t(body.error)` 原样翻译。于是每个服务端错误码都是翻译键，但它定义在另一个文件、另一种语言运行时、由另一位作者写下。
- **枚举标签。** 配置对象上的 `labelKey` 字段，通过 `t(meta.labelKey)` 翻译。

字面量扫描对这两类都是瞎的。在本仓库，这份沉默是有代价的：服务端错误码 `repo_index_kv binding is not available` 从四个调用点返回，却在所有文案包里都没有译文，于是中文界面会显示这串原始英文。

修法是结构性的，不是打补丁：**给每个动态键一个可枚举的来源，然后在测试里遍历这个来源。**

- 把错误码放进一张共享常量表，让服务端和测试都引用它——本仓库是 [`src/types.ts`](../src/types.ts) 里的 `ERROR_CODES`，该模块本来就是存放共享线格式类型的地方。同时收紧参数类型（`errorOutcome(status, error: ErrorCode)`），这样新的调用点就无法凭空造出一个没有任何文案包认识的码。
- 在测试里遍历该表，断言每个码在**每个**文案包中都存在——本仓库是 [`src/client/i18n.test.ts`](../src/client/i18n.test.ts) 里的 "translates every server error code"。

**绝不要把异常信息当作错误码发给客户端。** `catch` 块里的 `String(err)` 会把一个任何文案包都翻不了的字符串交给界面，并把内部细节泄露到用户可见的信息里。应该把细节记到服务端日志，只返回一个稳定的码——本仓库是 `ERROR_CODES.internalError`。

## 证明这条防线真的会拦

从未见过失败的断言不算证据。接完第 3 条或第 6 条之后，故意删掉一条译文，确认测试套件变红并指出缺失的键：

```
zh-cn missing: kvUnavailable -> "repo_index_kv binding is not available"
```

再把译文恢复，确认套件重新变绿。这一步常被跳过，而它是唯一能确认"防线覆盖了你以为它覆盖的场景"的办法。

## 什么情况下不该用这个范式

- **有复数变化复杂的语言**（俄语、阿拉伯语、波兰语、捷克语）。"英文整句作 key"加 `{0}` 占位符，等于放弃了运行时的复数支持：i18next 通过 `count` 选项和 `_one` / `_other` / `_few` / `_many` 后缀键选择复数形式（<https://www.i18next.com/translation-function/plurals>），而第 4 条的恒等映射断言会让带后缀的键根本写不出来。标准答案是 ICU MessageFormat：把 `plural` 与 `select` 参数放在同一条消息里，由译员按目标语言补上所需形式（<https://unicode-org.github.io/icu/userguide/format_parse/messages/>）。
- **字符串量很大，或流程里接了翻译平台。** 改写一句英文，就会让该键在所有语言里失效。规模上来后，语义化 key（`search.placeholder`）更好维护，也更好在翻译系统里往返。
- **文案改动频繁。** 原因同上，只是规模小、代价还能忍。

## 换技术栈时哪里要改

真正与技术栈绑定的只有一步：**从源码里找出被引用的键**。本仓库用的是 Vite 的 `import.meta.glob(..., { query: "?raw" })`，在测试时读取客户端源码。换到别的前端，用等价的 glob 即可；出了 JavaScript 就得自己写一个小扫描器。清单里其余各项都是约定与断言，可以原样带走。
